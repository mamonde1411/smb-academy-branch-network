### 어려웠던 점, 궁금했던 점과 답


**왜 요구사항 6, 7을 Port Security로는 만족시키지 못하고 802.1X로 만족시킬 수 있는가?**

Port Security에 대한 이해는 정확하십니다. 개수 제한 + 허용 MAC. 문제는 MAC이 무엇인가예요.

① MAC은 신원이 아니라 라벨입니다. 명령 한 줄로 바꿉니다. 그리고 허용된 MAC이 뭔지 알아내는 것도 어렵지 않아요 — 같은 네트워크에서 관찰만 해도 보입니다. 그 MAC으로 위장하면 Port Security는 그냥 통과시킵니다. 802.1X는 비밀(비밀번호나 인증서)을 증명해야 해서, 관찰만으로는 못 뚫습니다.

② 등록 관리가 현실에서 무너집니다. 신규 노트북마다 관리자가 MAC을 등록해야 하는데, 이건 요구사항 6("설정 없이 붙을 것")과 정면충돌이죠. 그래서 실무에서는 귀찮아서 sticky로 대충 열어두게 되고, 결국 아무 장비나 붙습니다.

③ 이게 결정적인데 — Port Security는 "누구"를 모릅니다. 포트에 몇 대가 붙었는지만 알지, 그게 강사인지 퇴사자인지 구분하지 못해요. 그래서 VLAN을 동적으로 줄 수가 없고, 직무별 분리가 원리적으로 불가능합니다.

한 줄로 정리하면:

Port Security는 "몇 대까지, 어떤 라벨의 기계까지"를 통제하고, 802.1X는 "누구인지"를 통제한다.

요구사항 1(직무별 분리)과 2(퇴사자 차단)는 둘 다 "누구"의 문제입니다. 그래서 Port Security로는 못 풉니다. 이 문장이 §3 표의 "탈락 기술" 칸에 그대로 들어갈 답이에요.

다만 Port Security를 버리진 않습니다. 802.1X를 지원하지 않는 장비가 있거든요 — 복합기, 바코드 스캐너, IP 카메라 같은 것들이요. 학원에도 있을 겁니다. 그런 장비를 어떻게 처리할지는 생각해보실 문제고, 이걸 다루는 별도 기법이 있다는 것만 알려드릴게요. 범위를 늘릴지는 나중에 판단하시죠.

| | Port Security (번호판) | 802.1X (신분증) |
|---|---|---|
| 위조 | MAC은 명령 한 줄로 바꿈. 남의 MAC은 관찰만 해도 보임 | 비밀번호·인증서를 증명해야 함. 훔쳐보기로는 안 됨 |
| 등록 부담 | 기기마다 관리자가 등록 → 요구사항 6과 충돌 | 사람에게 계정 하나. 기기는 무제한 |
| "누구"를 아는가 | 모름. 몇 대 붙었는지만 앎 | 앎. 그래서 직무별 VLAN을 줄 수 있음 |

Port Security는 "몇 대까지, 어떤 라벨의 기계까지"를 통제하고, 802.1X는 "누구인지"를 통제한다.

3. Port Security vs 802.1X — 기능으로만

Port Security는 스위치 포트에서 동작합니다. 포트로 들어온 프레임의 출발지 MAC 주소를 읽어서, 그 포트에 허용된 MAC 목록과 최대 개수를 검사합니다. 위반하면 포트를 차단하거나 해당 프레임을 버립니다. 판단 근거는 오직 MAC 주소 하나이고, 판단은 스위치가 자기 테이블만 보고 내립니다.

802.1X는 포트를 인증 전 상태로 둡니다. 이 상태에서는 인증용 프레임 외에는 아무것도 통과하지 못합니다. 단말이 자격증명을 제출하면 스위치·WLC가 그걸 RADIUS 서버로 전달하고, RADIUS가 검증한 뒤 허용/거부와 함께 VLAN 같은 정책 값을 돌려줍니다. 그 응답을 받고 나서야 포트가 열리고 지정된 VLAN에 배정됩니다.

차이를 네 가지로 정리하면:

| | Port Security | 802.1X |
|---|---|---|
| **검사 대상** | MAC 주소 — 프레임에 그대로 실려 있고 변경 가능 | 자격증명 — 검증 절차를 거쳐야 함 |
| **판정 주체** | 스위치의 로컬 테이블 | 중앙 RADIUS 서버 |
| **결과의 형태** | 허용 / 차단 (이진) | 허용 + VLAN·정책 값 반환 |
| **상태 관리** | 정적 등록 | 세션 기반 — 재인증·세션 종료 시 자동 회수 |

세 번째가 결정적입니다. Port Security의 결과에는 직무를 나눌 정보가 애초에 담기지 않습니다. 통과시킬지 말지만 있고 "이 사람은 어느 그룹"이라는 값이 없어요. 그래서 요구사항 1(직무별 분리)에 쓸 수가 없습니다.

두 번째도 중요합니다. 판정이 중앙에 있으면 계정 하나를 비활성화하는 것으로 모든 스위치와 AP에서 동시에 차단됩니다. 로컬 테이블 방식은 장비마다 일일이 지워야 하고요.

### 피드백 권한은 개발 영역에서 나누나?

층별로 권한이 다르다.
**자원에 도달하는가는 네트워크, 그 자원을 다룰 수 있는가는 서버, 자원 안의 무엇을 다루는가는 애플리케이션**


| 층 | 답하는 질문 | 예 |
|---|---|---|
| 네트워크 | 피드백 서버에 닿을 수 있나	| 강사·프런트 허용, 도서관리 차단 |
| 서버·계정 | 그 폴더를 읽기만? 쓰기도?	| 강사는 쓰기, 프런트는 읽기 |
| 애플리케이션 | 어느 학생의 피드백을 보나	| 강사는 자기 반 학생만 |


<u>읽기/쓰기 권한이 왜 네트워크층에서 안 되나?</u>
네트워크 장비로는 못함. 라우터와 스위치는 IP 패킷을 보고 통과/차단만 결정함.
"이 사람이 이 폴더를 수정해도 되나"는 파일 서버의 운영체제가 판단하는 일.
네트워크 장비는 그 판단에 아예 관여 X.

그리고 현실적인 이유도 있습니다 — Packet Tracer에는 진짜 파일 서버가 없습니다. PT의 Server 장치는 HTTP·DHCP·DNS 같은 서비스를 흉내낼 뿐이라, 공유 폴더도 그룹 권한도 만들 수 없어요. 그래서 A에서는 검증 자체가 불가능합니다.

**네트워크**는 "어느 IP에서 어느 IP의 어느 포트로 가는 패킷"만. 그 안에 누구의 피드백이 들었는지는 모르고 알 방법도 없음.
**파일 서버**는 "이 사용자가 이 폴더에 접근 가능한가"를 봄.
**애플리케이션**은 DB에서 "이 강사가 맡은 반 → 그 반의 학생들"을 조회해서 그것만 보여줌 관계를 이해하는 유일한 층.
